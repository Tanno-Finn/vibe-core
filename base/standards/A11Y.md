# A11Y — base standard (accessibility)

This is an **educational** portal: if a learner cannot perceive or operate the content,
the product has failed at its one job. Accessibility is therefore a base standard, not a
kit nicety.

Most rules are `[hard]`. A few are `[overridable]` — a project may relax them *in the
open* via an [override](../../overrides/README.md), which turns the gate from blocking
into advisory (a visible warning), **never off**.

| ID | Rule | Tag | Why (plain language) |
|---|---|---|---|
| A11Y-001 | Every interactive element is keyboard-reachable and operable; visible focus is never removed. | `[hard]` | Many people navigate without a mouse. An unreachable control is a broken control. |
| A11Y-002 | Every meaningful image / icon has a text alternative; decorative ones are marked empty. | `[hard]` | Screen-reader users and failed image loads both depend on the text alternative. |
| A11Y-003 | Interactive canvas / custom widgets expose a keyboard path and an ARIA role or label. | `[hard]` | A demo you can only reach with a mouse excludes keyboard and screen-reader learners. |
| A11Y-004 | Text and essential UI meet WCAG AA contrast (4.5:1 body, 3:1 large / UI). | `[hard]` | Low contrast is the single most common reason people can't read a page. |
| A11Y-005 | Ship an Easy-Language (simplified) path for primary content where the kit supports it. | `[overridable]` | Simplified language reaches learners with reading difficulties — but a niche internal tool may legitimately skip it. Document the reason. |
| A11Y-006 | Don't convey meaning by color alone; pair it with text, shape, or icon. | `[hard]` | Color-blind users miss color-only signals entirely. |
| A11Y-007 | Respect `prefers-reduced-motion`; no essential information lives only in animation. | `[overridable]` | Motion can cause nausea and distraction. A deliberately animation-first showcase may override — with a documented reason and a still fallback. |

**How to check:** the kit's health checks include an automated accessibility pass on the
built pages (health check `a11y-built-pages`); `[hard]` failures block, everything else
warns.

In this kit that pass is `npm run check:a11y` ([`scripts/check-a11y.mjs`](../../scripts/check-a11y.mjs)),
run after `npm run build:prod` and in CI after the production build. What it does:

- serves the production output (`dist/vibecore/browser`) from a local static server and
  opens, in headless Chrome, the prerendered home, first article, glossary, demos hub,
  timeline, sources, settings, and Impressum pages in German and English, plus home and the article
  again with Easy Language switched on — each in a light and a dark color scheme;
- runs [axe-core](https://github.com/dequelabs/axe-core) on the hydrated page, with
  transitions and animations frozen so a half-finished fade is not measured;
- attributes each axe violation to an A11Y rule through a fixed, commented map in the
  script (e.g. `color-contrast` → A11Y-004, `image-alt` → A11Y-002, `button-name` and the
  ARIA attribute rules → A11Y-003, `nested-interactive` → A11Y-001,
  `link-in-text-block` → A11Y-006) and reads each rule's tag from the table above. A
  violation of a `[hard]` rule fails the run, and so would one of an `[overridable]` rule
  without a valid override (no axe rule maps to A11Y-005 or A11Y-007 today); unmapped axe
  findings (landmarks, heading order, …) are printed as advisory.
- keeps a short `KNOWN` list in the script for `[hard]` violations that are real but
  whose fix is a design decision: each names the exact axe rule and element, says why it
  is not fixed and points at `OPEN-QUESTIONS.md`, and is printed on every run. It is an
  admission, never a filter — it only shrinks, and an entry that stops matching is
  reported as stale. (Empty since 2026-09-22: both entries it started with were fixed.)

The Easy-Language *coverage* behind A11Y-005 is counted by a different gate:
`scripts/check-content-coverage.mjs` (part of `npm run build:prod`) pins the number of
entries without an Easy-Language file per collection and fails the build when it grows.
One collection is exempt by an explicit policy in that script: `sources` is
*bibliographic* — a title must name the work exactly — so its Easy locales use the
base-language record by design and are reported separately, never counted as backlog.
That regression — and only that finding — turns advisory under a valid
`overrides/A11Y-005.md`; [`overrides/README.md`](../../overrides/README.md) lists every
gate that honors an override.

What it **cannot** check, and what therefore stays manual review: whether the keyboard
path through a canvas demo makes sense, focus order, whether alt text is *meaningful*,
color-only meaning inside images, reduced-motion behavior (A11Y-007), whether
Easy-Language text is actually easy (A11Y-005), any page not in the list above, and any
state that needs a click — open menus, dialogs, demo steps. A green run means "no
machine-detectable violation on these pages", not "accessible".
